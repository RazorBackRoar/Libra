# Libra — macOS Application Audit

**Status: audit only. No files were modified, no branches or tags touched, nothing built, signed, or released.** I did not have time to finish every section of your master prompt; what follows is what I actually inspected, with the gaps marked.

---

## 1. Executive summary

Libra is a native Swift/SwiftUI macOS media-organization app built with Swift Package Manager (no Xcode project, no third-party dependencies). It scans folders, probes media with AVFoundation/ImageIO, previews a plan, and — only on explicit Write — renames, sorts, or transforms files, keeping an in-memory undo journal.

The engineering state is better than most projects this size: zero external dependencies, a real safety model (preview-first, containment checks, symlink rejection), genuine cancellation plumbing, and honest documentation about what is heuristic versus measured. Major architectural change is **not** warranted.

The headline problem is a shipped functional regression: **both ffmpeg-backed tools cannot write output at all**, and preview masks it. Second is a version/provenance break: the DMG on disk is stamped `1.2.4` but contains code from 10 commits past the `v1.2.4` tag.

## 4. Critical problems

### 4.1 Slo-Mo and 1-Min-Adjuster cannot produce output — ESSENTIAL

**Finding:** Every ffmpeg write fails. `runToUniqueOutput` writes to `outputPath + ".libra-tmp"` and passes no `-f` format flag, so ffmpeg cannot select a muxer.

**Evidence:** `FfmpegOps.swift:88` builds the temp path; `:26–32` and `:56–63` pass it as the output argument with no `-f`. I reproduced it with the exact argument patterns (ffmpeg 6.1.1, Linux — **not** your macOS Homebrew build):

```
Unable to choose an output format for 'out.mp4.libra-tmp';
use a standard extension for the filename or specify the format manually.
exit code 234, no output file created
```

Regression introduced 2026-08-15 in `8f31074`; the prior version wrote straight to `outputPath` with a real extension. It is therefore in the shipped `v1.2.4`.

**Why it went unnoticed:** the preview path short-circuits before ffmpeg (`ToolState.swift:607–613`, `:669–675`) and always reports success. Only a live Write hits it, surfacing as `"Error opening output files: Invalid argument"`.

**Smallest fix:** keep the temp name but pass the real container explicitly — derive the muxer from the final extension and add `-f <fmt>`, or suffix as `<name>.libra-tmp.<ext>`.

**Priority:** Essential · **Benefit:** Correctness · **Risk:** Low · **Confidence:** High

### 4.2 Version/provenance mismatch on the built DMG — ESSENTIAL

**Finding:** `build/Release/Libra.dmg` declares `1.2.4` but contains post-tag code.

**Evidence:** Extracted the DMG; `Info.plist` and both `version.json` copies read `1.2.4`. Strings added in `d493a50` (`"Drop a folder or videos above."`, `"No videos in this category."`, `"Drop photos here"`, `"Select Photos"`) are **present** in the shipped Mach-O; strings removed in the same commit (`"Has location"`, `"Apple device"`) are **absent**. So the artifact is built from current `main`, 10 commits past `v1.2.4`.

`version.json` is the single version authority, and `CFBundleVersion` and `CFBundleShortVersionString` are both set from it — there is no build number to disambiguate rebuilds.

**Recommendation:** bump `version.json` before packaging; consider deriving `CFBundleVersion` from the commit count or short SHA so an artifact identifies its source.

**Priority:** Essential · **Benefit:** Release integrity · **Risk:** Low · **Confidence:** High

### 4.3 The release build cannot be reproduced from this repository — ESSENTIAL

**Finding:** `scripts/build-mac.sh` depends on scripts outside the repo:

```
RAZORCORE_DIR="$(cd "$SCRIPT_DIR/../../.razorcore" && pwd)"
"$RAZORCORE_DIR/patch-app-branding.sh" "$APP_PATH"
"$RAZORCORE_DIR/package-dmg.sh" --app ... --dmg ...
```

`.razorcore` is the grandparent directory — not in the ZIP, not in git. With `set -e`, a clean clone fails at the `cd`. DMG layout, volume icon, and background all come from an unversioned external script.

**Priority:** Essential · **Benefit:** Release integrity, Maintainability · **Risk:** Low · **Confidence:** High · *Potential shared RazorBackRoar standard.*

### 4.4 Preferences menu item probably does nothing — ESSENTIAL

`AppDelegate.showSettings()` sends `Selector(("showPreferencesWindow:"))` (`LibraApp.swift:126`). Apple renamed this to `showSettingsWindow:` for apps built against the macOS 13+ SDK — this app is built against **26.5**. Because `buildMenu()` replaces the entire main menu, this is the only route to the `Settings` scene (⌘,).

The supported public API at your macOS 14 floor is `@Environment(\.openSettings)` or `SettingsLink`. Your own audit rules forbid private selectors; this is one.

**Confidence:** Medium-High (static reasoning; not run).

### Performance (analysis only — nothing profiled)

- **Per-file progress** hops to the main actor and mutates `@Published` once per file (`Scanner.swift:146` → `ToolState.swift:243–250`), re-evaluating `videoWorkspace` each time. That re-runs `orderedResults` (full sort, `ResultsTable.swift:8–15`), `DuplicateDetector.extraPaths` (`ToolPage.swift:79`) and `CountPills`. Coalescing progress to ~10/sec is the single highest-value fix.
- **`commitMove` copy-on-write:** `reservedSnapshot` stays in scope while `reserved.insert(...)` mutates, forcing a Set copy per file — O(N²). `ToolState.swift:396–401`.
- **Directory walk** uses legacy `enumerator(atPath:)` plus `fileExists` **and** `isSymlinkOrAlias` (which does `.isAliasFileKey`) per entry. `enumerator(at:includingPropertiesForKeys:)` with prefetched keys is the modern equivalent. `Scanner.swift:222–232`.
- **DateFormatter churn:** new formatter per file in `extraFolderParts` (`ToolState.swift:698`) and per metadata item in `parseDate`/`parseExifDate` (`MediaProbe.swift:496–512`).
- **Clustering** allocates a `CLLocation` inside the inner comparison loop, with an O(C³)-worst-case merge. `GPSMapModel.swift:130–134, 195–201`.
- `-c:v libx264` ignores the Apple Silicon media engine; `h264_videotoolbox` is the ARM-native option, with a quality trade-off. `FfmpegOps.swift:30`.

### Accuracy (your §14) — see also §24 for the authoritative resolution/FPS classification spec

Identification rows show `FileNaming.fpsBucket(file.fps)` — a snapped 24/30/60/120 bucket, not the probed rate. A 29.97 fps clip reads "30 fps". The README promises "fps". `MediaIdentification.swift:12`. Separately, `fps` comes from `.nominalFrameRate`, which is approximate for variable-frame-rate video — worth stating rather than implying precision.

**Resolution classification is now fully specified in §24**, including the seven-bucket scheme (SD, 720p, HD, 1080p, FHD, QHD, 4K), boundary logic, ±2px tolerance rules, and the check order that makes it work. FPS snapping rules (snap to nearest of 30/60/120) are also defined there with edge-case tables from real data.

## 12. Corrections to Part 1

**The "FHD" bucket is intentional and tested, not a defect.** `MediaClassificationTests.swift:6–13` contains `testResolution_1080pIsNotFHD`, which explicitly asserts `2048×1080 → "FHD"` and `1920×1080 → "1080p"`. This is a deliberate, locked-down contract. Withdraw it as a finding; only the README/docs never explain the distinction to users, which is a documentation gap at most. **Note: §24 now provides the authoritative replacement for these old bucket names and their boundaries.**

**The Gatekeeper claim is now verified.** Apple confirmed on its developer site that "In macOS Sequoia, users will no longer be able to Control-click to override Gatekeeper when opening software that isn't signed correctly or notarized," and users must instead go to System Settings > Privacy & Security to review the software before allowing it. Before Sequoia, Control-clicking an app in Finder was the standard override; Apple removed that bypass. Libra requires macOS 14+ and is built against the 26.5 SDK, so most users land on 15 or 26 and the README instruction fails them. Note Libra is *ad-hoc signed*, not unsigned — ad-hoc local signing satisfies the Apple Silicon signing requirement, and the Privacy & Security path applies to signed-but-not-notarized apps — so "Open Anyway" should work; it's the instruction that's wrong, not the distribution model.

## 14. Testing review

74 test functions across 14 XCTest files, ~1,300 lines. Quality is genuinely good where coverage exists: `FileOpsTests` (18 tests) covers symlink rejection, parent-symlink escape, never-overwrite, reserved-set batching, and the padded-index uniquifier; `ScannerServiceTests` covers cancellation-preserves-partial-results and continue-after-one-failure; `ProcessRunnerTests` covers timeout, cancellation, and stderr pipe drain. That is real regression protection on the dangerous paths.

**The coverage gap is exactly where the shipped bug lives.** `FfmpegOps` has one test — `testFfmpegOpsTimeoutCalculations`, pure arithmetic on `timeout(durationSec:factor:)`. Nothing tests argument construction or the output path, which is why §4.1 shipped. Also untested: `DryRunReport`, `PhotoMover`, `Updates.compareVersions` (pure and trivially testable), `AppState` dependency resolution, `Resources.bundle`, `Logging`.

**Three test-hygiene defects, all confirmed by reading:**

1. **The test suite writes files to your real Desktop.** `testScheduleRerunPreviewsWhenLiveToggleOff` (`ToolStateTests.swift:22–32`) sets `state.files = [stubVideo()]` and sleeps 700 ms — past the 450 ms debounce — so a real preview pass runs, reaching `applyRunRecap` → `DryRunReport.write` → `~/Desktop/Libra Sorter Dry Run N.txt`. Every `swift test` run leaves another numbered file on the Desktop, locally and on CI.
2. **Tests mutate real persisted user settings.** `testMovePhotosOutRefusesDestinationInsideSource:51` calls `SettingsStore.shared.update { $0.lastFolder = "/Trip" }`, which writes `~/Library/Application Support/Libra/settings.json` and never restores it. Singleton state also leaks between tests in-process.
3. **A fire-and-forget Task.** `testStartScanClearsUndoRecords` calls `startScan(paths: ["/tmp/empty-scan"])` and returns without awaiting; the scan Task outlives the test.

`Libra.progress.md` claims "Full `swift test` — 17/17 passed". There are now 74 test functions — the claim is stale by a wide margin. The same file asserts "No personal Desktop paths remain in source/tests", which is **false**: `Tests/LibraTests/ScanSafetyTests.swift` has `/Users/home/Desktop/MetaBurn & Libra Test/videos` at lines 6, 8, and 23.

## 15. Diagnostics review

Only `Log.shared.info` is ever called — two sites, both in `ToolState`. `debug`, `warn`, and `error` have **zero** call sites repo-wide. So a failed move, a metadata probe failure, a geocode failure, and an ffmpeg error all vanish without a log line; the user gets a UI string and nothing persists. Given §4.1 shipped silently, that matters.

The dual-sink design (os.log `Logger` + a file) duplicates the timestamp and level that `os_log` already records. The file sink has no rotation or size cap, builds an `ISO8601DateFormatter` per line, and does open/seek/write/close per line — on the main actor, since `Log` is `@MainActor`. Low volume today because almost nothing logs; it would become a main-thread I/O problem the moment you add per-file logging.

No sensitive data is logged. `AppInfoProvider.printStartupInfo()`'s `print()` banner is documented as intentional in AGENTS.md, and I'm leaving it alone as instructed.

## 16. Agent / governance layer — a live contradiction

Your most recent commit on `main` (`d8e3ef2`, "docs(jules): retire sentinel/bolt/palette daily audit contract (#100)") states in AGENTS.md: *"Daily sentinel / bolt / palette audit branches are retired. Do not create `sentinel-*`, `bolt-*`, or `palette-*` branches."*

Two related concerns:

- **`.jules/bolt.md` carries a standing instruction that would break your overwrite protection.** Its recorded "learning" recommends replacing `FileManager.default.fileExists` loops with a cached `contentsOfDirectory` Set, and explicitly acknowledges the case-sensitivity behavior change. The only such loop in the codebase is `FileOps.uniquePath` — the function that stops Libra from colliding with the user's existing files. Applying that "learning" would trade a correct check for a stale in-memory snapshot in the one place where being wrong destroys data.
- **`.jules/config.json` sets `auto_approve_plans: true` and `suggestions.auto_execute: true`**, and AGENTS.md reinforces it ("Do not pause or wait for human plan approval on routine refactoring"). **Recommendation:** delete or rewrite the three `.jules/*.md` files to match AGENTS.md; remove the `FileOps.uniquePath` "learning"; set `auto_approve_plans: false` for changes touching `Services/FileOps.swift`, `Services/FfmpegOps.swift`, `Services/UndoApply.swift`, `scripts/`, and `.github/`. *Potential shared RazorBackRoar standard.*

## 17. Duplication: two implementations of "move photos out"

`LibraView` routes `.photoSweep` to `PhotoSweepView` and everything else to `ToolPage`. `PhotoSweepState` (287-line file) re-implements `photos`/`results`/`running`/`recap`/`dryRun`/`progress`/`undoRecords`, `startScan`, `moveOut`, `undoLastRun`, `beginScan`, `confirmFileCount`, and `browse` — all of which `ToolState` + `ToolPage` already have for the Photos tab.

Safety has **not** drifted: both check `ScanSafety.destinationIsInsideSource` and both honour `requireConfirmToWrite`. Behaviour has:

| | `ToolState.movePhotosOut` | `PhotoSweepState.moveOut` |
|---|---|---|
| Removing moved photos | `Set`-based, O(N) (`:176–177`) | nested `contains`, **O(N²)** (`:85–87`) |
| Results array | `append(contentsOf:)` | `results = moved` (replaces) |
| Desktop Dry Run report | written | **not** written |

That last row contradicts the README's "Desktop reports … (tool name swaps per mode)" for the Photos Only tile. Not urgent, but this is the kind of drift that eventually produces a real safety divergence. Consolidating on `ToolState` with `tool == .photoSweep` is the smaller long-term liability.

## 21. Recommended build / release architecture

Keep the local script as the developer path; add CI as the artifact authority:

```
version.json bump  →  commit  →  tag vX.Y.Z  →  push tag
     ↓
CI (macos-26, arm64) on tag:
  swift build -c release   →  swift test
  scripts/build-mac.sh     (now self-contained per #3)
  codesign --sign - (ad-hoc, no --deep)
  verify: lipo -archs == arm64 · Info.plist version == tag · codesign --verify
  create GitHub Release, attach Libra.dmg
```

Three properties this buys you that the current process cannot: the artifact provenance is a tag, not a timestamp; the version/architecture/signature checks are enforced rather than remembered; and `swift build -c release` is exercised on every tag instead of only when you happen to package.

Notarization is the one thing that would remove the Gatekeeper friction entirely — it needs a paid Apple Developer account, and it's a legitimate choice to keep skipping it. If you do skip it, fix the README instruction (§12) rather than leaving users stuck.

## 23. Native metadata pipeline specification

Correct. You don't need FFmpeg for this.

For a native Swift/macOS video metadata reader, I'd keep the entire metadata pipeline Apple-native:

* AVFoundation — video/container metadata, tracks, duration, resolution, frame rate, codec, HDR, creation date, location metadata, camera metadata where embedded.
* Core Media — precise timing, format descriptions, media characteristics.
* Foundation — file URLs, filesystem creation/modification dates, file size.
* Core Location — interpret GPS coordinates and optionally convert them into a human-readable location.
* ImageIO — useful when metadata is actually EXIF/image metadata rather than QuickTime metadata.
* Uniform Type Identifiers (UTType) — determine the media/container type.

For your use case, the architecture should essentially be:

Video file
    ↓
AVAsset
    ↓
AVMetadata / AVAsset metadata
    ├── Camera make
    ├── Camera model
    ├── Lens
    ├── Creation date
    ├── GPS latitude
    ├── GPS longitude
    └── Location
    ↓
AVAssetTrack
    ├── Resolution
    ├── Frame rate
    ├── Codec
    ├── HDR
    └── Color information
    ↓
Foundation
    ├── File creation date
    ├── Modification date
    └── File size

No FFmpeg, no ffprobe, no shelling out to an external executable.

For an ARM-native macOS app, that's also the cleaner approach because the metadata reader is implemented directly against Apple's frameworks rather than carrying an enormous third-party multimedia stack.

One important distinction: metadata availability depends on what the video actually contains. An iPhone video may contain camera/GPS/date metadata, while a downloaded or re-encoded video may contain only some of those fields. Your reader should therefore treat every field as optional rather than assuming it exists.

For Libra specifically, I would use Apple's APIs to determine the authoritative values for resolution and frame rate, rather than trying to parse those values from filenames or relying on FFmpeg.

I need you to fix Libra’s video metadata handling and related video-processing behavior. Work through this entire specification in order, step by step, and do not skip, simplify, or omit any requirement below.

The goal is to make Libra a fully native Swift/macOS video organizer using Apple’s native frameworks for video inspection and metadata. Do not use FFmpeg, ffprobe, or any external multimedia command-line tool.

### 23.1 Use Apple-native frameworks only

For video metadata and video characteristics, use Apple's native frameworks:

### 23.2 Create a dedicated video metadata reader

Libra should have a clear, dedicated Swift component responsible for extracting metadata from each video.

Use a normalized metadata model so Libra gets a consistent representation regardless of whether the source is an iPhone MOV, MP4, or another supported video container.

The metadata model must support optional values because not every video contains every metadata field.

* Longitude

If the video has no GPS metadata, leave the location fields unavailable.

### 23.6 Read video duration

Use AVFoundation/Core Media to determine the video's duration.

Do not use filename parsing or external command-line utilities.

The normalized metadata must expose duration in a form that Libra can reliably use for display and processing.

### 23.7 Read resolution correctly

Resolution must come from the actual video track.

3840 × 2160
1920 × 1080
1280 × 720

Do not infer resolution from the filename when the actual video track can provide it.

Do not assume that a filename containing 4K, 1080p, HD, etc. is authoritative.

The actual encoded media characteristics must be the source of truth.

**Once the raw resolution is obtained, classify it into one of the seven buckets defined in §24.**

### 23.8 Read frame rate correctly

Frame rate must come from the actual video track/media format.

Support fractional and common video frame rates, including:

23.976 fps
24 fps
29.97 fps
30 fps
59.94 fps
60 fps

Do not round values prematurely.

For example, preserve 59.94 rather than displaying it as 60 when the underlying media reports 59.94.

This is particularly important for Libra's filename-generation logic because frame rate is part of the information Libra uses when organizing videos.

**For filename generation and folder naming, snap the raw frame rate to the nearest of [30, 60, 120] as defined in §24. The raw rate is preserved for display; the snapped rate is used for filenames.**

### 23.9 Read codec information

Use AVFoundation/Core Media to identify the actual video codec/format.

The metadata reader should distinguish relevant codecs such as HEVC/H.265, H.264, and other formats supported by Apple's media frameworks.

Use the actual media track rather than guessing from the filename extension.

### 23.10 Read HDR and color information

Where the source media exposes it, inspect the video's HDR/SDR and color characteristics.

Support information such as:

* HDR vs SDR
* Color space
* Transfer characteristics
* Video range
* Other relevant media/color properties exposed by Core Media and AVFoundation

Do not invent HDR information when it cannot be established from the source.

### 23.11 Read orientation correctly

Account for the video's orientation/transform.

Do not assume that the raw encoded dimensions alone represent the way the video should be displayed.

A video may have encoded dimensions that need to be interpreted together with its preferred transform.

Libra should distinguish between the underlying encoded dimensions and the effective displayed orientation where necessary.

**For filename generation, use the orientation rules defined in §24: V (portrait) when height > width, W (landscape) otherwise, applied after the preferred transform.**

### 23.12 Read audio information where available

Support information such as:

* Audio format
* Codec
* Sample rate
* Channel count
* Other relevant audio-track information exposed by AVFoundation/Core Media

If a video has no audio track, handle that normally.

### 23.13 Read filesystem information

Use Foundation for filesystem-level information, including:

* File size
* Filesystem creation date
* Filesystem modification date
* File URL/path
* Uniform Type Identifier where appropriate

Keep filesystem metadata separate from embedded media metadata.

* Shell out to FFmpeg
* Shell out to ffprobe

### 24.3 Logic breakdown

The naming system has four components, each determined by a single, independent rule. No component depends on another — they can be evaluated in any order.

#### 24.3.1 Resolution bucket

**Input:** `width` and `height` (integers, pixels)
**Derived value:** `longEdge = max(width, height)`
**Output:** One of 7 strings

```
┌─────────────────────────────────────────────────────┐
│                  RESOLUTION LOGIC                    │
│                                                      │
│   longEdge = max(width, height)                      │
│                                                      │
│   if longEdge ≥ 3840         → "4K"                  │
│   if |longEdge − 2560| ≤ 2  → "QHD"                 │
│   if |longEdge − 1920| ≤ 2  → "1080p"               │
│   if longEdge > 1920         → "FHD"                 │
│   if |longEdge − 1280| ≤ 2  → "720p"                │
│   if longEdge > 1280         → "HD"                  │
│   else                       → "SD"                  │
└─────────────────────────────────────────────────────┘
```

**Why this order matters:**

The checks are **not** a simple "nearest standard" lookup. Order matters because tolerance checks must run **before** range checks:

1. `≥ 3840` catches all 4K and above (including 8K, 5K — they're all "4K" now)
2. `|longEdge − 2560| ≤ 2` catches exactly 2558–2562 **before** the next range check could grab it
3. `|longEdge − 1920| ≤ 2` catches exactly 1918–1922 **before** `> 1920` grabs it
4. `> 1920` is the FHD range — everything between 1922 (exclusive) and 2558 (exclusive)
5. `|longEdge − 1280| ≤ 2` catches exactly 1278–1282 **before** `> 1280` grabs it
6. `> 1280` is the HD range — everything between 1282 (exclusive) and 1918 (exclusive)
7. `else` is SD — everything below 1278

**The ±2px tolerance:**

Three standards get a ±2px tolerance window: **2560**, **1920**, **1280**. This exists because video encoders sometimes round dimensions by 1–2 pixels for alignment (H.264/H.265 macroblock boundaries). From the real data:

| Standard | Tolerance window | Seen in dataset |
|----------|-----------------|-----------------|
| 2560 | 2558–2562 | 2560 ✓ |
| 1920 | 1918–1922 | 1920 ✓, 1918 (not seen), 1922 (not seen) |
| 1280 | 1278–1282 | 1280 ✓, 1278 ✓ |

**4K has no tolerance window.** It uses `≥ 3840`, not `|longEdge − 3840| ≤ 2`. This is intentional — there's no meaningful resolution "just below" 4K that should round up. Everything from 3840 to infinity is 4K.

**The seven buckets visualized on a number line:**

```
Long edge:  0          1278  1282       1918  1922       2558  2562       3840        ∞
            ├────SD────┤720p├───HD──────┤1080p├───FHD────┤ QHD ├───4K──────────────────┤
                       ±2px             ±2px             ±2px
```

**What the dataset actually contains:**

| Bucket | Long edges seen | Source devices |
|--------|----------------|----------------|
| 4K | 3840 | iPhones (4K mode), some cameras |
| QHD | 2560 | Mac screen recording (1 video) |
| FHD | 2436, 2796 | iPhone X/14 Pro screen recordings |
| 1080p | 1920 | iPhones (1080p mode), screen recordings |
| HD | 1620, 1744, 1898, 1910, 1916 | iPad screen recordings, cropped exports |
| 720p | 1278, 1280 | Social media downloads, older recordings |
| SD | 128–960 | iMessage clips, social media, thumbnails |

#### 24.3.2 Orientation

**Input:** `width` and `height` (integers, pixels)
**Output:** `V` (vertical/portrait) or `W` (wide/landscape)

```
if height > width → "V"
else              → "W"
```

Square videos (width == height) fall to `W`. This almost never happens in practice — zero instances in the 834-file dataset.

| Orientation | Count | Percentage | Typical sources |
|-------------|-------|------------|-----------------|
| V (portrait) | 465 | 55.8% | Phone recordings held vertically, phone screen recordings |
| W (landscape) | 369 | 44.2% | Phone held horizontally, Mac/iPad screen recordings, cameras |

#### 24.3.3 Frame rate

**Input:** `nominalFrameRate` (Float, from AVFoundation)
**Output:** One of three integers: `30`, `60`, or `120`

```
Snap to whichever of [30, 60, 120] is nearest:

  |fps − 30| vs |fps − 60| vs |fps − 120|  → pick smallest distance
```

**Why snap, don't round:**

Raw frame rates from AVFoundation are almost never exactly 30.000 or 60.000. They're NTSC-derived fractional rates or slight encoding variations:

| What it actually is | Raw value seen | Snaps to |
|---------------------|---------------|----------|
| 30fps (NTSC 30/1.001) | 29.970 | 30 |
| 30fps (exact) | 30.000 | 30 |
| 30fps (slight drift) | 29.890–30.090 | 30 |
| 60fps (NTSC 60/1.001) | 59.940 | 60 |
| 60fps (exact) | 60.000 | 60 |
| 60fps (slight drift) | 59.634–60.007 | 60 |
| 120fps | 119.950 | 120 |
| 24fps (film) | 23.999, 24.000 | 30 |
| 15fps (iMessage) | 15.000 | 30 |
| ~48fps (slo-mo crop?) | 48.195 | 60 |

**Edge cases from the real dataset:**

| Raw FPS | Distance to 30 | Distance to 60 | Snaps to | Source |
|---------|----------------|----------------|----------|--------|
| 15.000 | 15 | 45 | **30** | iMessage micro-clips (128×224) |
| 18.903 | 11.1 | 41.1 | **30** | Unknown (possibly corrupted) |
| 23.825 | 6.2 | 36.2 | **30** | iPad screen recording |
| 41.149 | 11.1 | 18.9 | **30** | Unknown social media clip |
| 44.101 | 14.1 | 15.9 | **30** | Mac screen recording (QHD) |
| 44.690 | 14.7 | 15.3 | **30** | iPad screen recording |
| 45.292 | 15.3 | 14.7 | **60** | Crossover point — barely 60 |
| 48.195 | 18.2 | 11.8 | **60** | Slo-mo crop artifact |
| 51.230 | 21.2 | 8.8 | **60** | Screen recording (variable rate) |
| 54.197 | 24.2 | 5.8 | **60** | Screen recording (variable rate) |
| 119.950 | 90.0 | 60.0 | **120** | iPhone slo-mo at 120fps |

The snap boundary between 30 and 60 is at exactly **45fps**. A video at 44.9fps snaps to 30; at 45.1fps it snaps to 60. In this dataset, `44.690` → 30 and `45.292` → 60. Both are screen recordings with variable frame rates — neither is "really" 30 or 60, but snapping is the best we can do without analyzing every frame.

| Snapped FPS | Count | Percentage |
|-------------|-------|------------|
| 30 | 262 | 31.4% |
| 60 | 571 | 68.5% |
| 120 | 1 | 0.1% |

#### 24.3.4 Padded number

**Input:** Sequential index (1-based)
**Output:** Zero-padded to 3 digits

```
index 1   → "001"
index 42  → "042"
index 834 → "834"
```

This is purely sequential — the order comes from the filesystem enumeration, not from any metadata sort. In a real implementation, this would be the file's position after sorting by whatever the user chose (date, name, etc.).

### 24.4 Combined logic — pseudocode

```
function classifyVideo(width, height, rawFPS):
    // 1. Resolution
    long = max(width, height)
    if long >= 3840:            resolution = "4K"
    else if |long - 2560| <= 2: resolution = "QHD"
    else if |long - 1920| <= 2: resolution = "1080p"
    else if long > 1920:        resolution = "FHD"
    else if |long - 1280| <= 2: resolution = "720p"
    else if long > 1280:        resolution = "HD"
    else:                       resolution = "SD"

    // 2. Orientation
    orientation = (height > width) ? "V" : "W"

    // 3. Frame rate
    fps = nearest([30, 60, 120], rawFPS)

    return resolution, orientation, fps

function generateName(width, height, rawFPS, index):
    res, ori, fps = classifyVideo(width, height, rawFPS)
    return "Apple {res} {ori}{fps} {index:03d}"
```

### 24.5 Swift implementation (for Libra)

These are the exact functions to wire into Libra. `resolutionClass` replaces the old 8-bucket function in `MediaClassification.swift`. `fpsClass` replaces `fpsBucket` in `FileNaming.swift`. `orientation` is new or replaces the existing orientation logic.

```swift
/// Seven fixed tiers. Long edge decides the bucket; the three named
/// standards (QHD, 1080p, 720p) keep a ±2px tolerance for encoder
/// rounding. Everything else falls into the range bucket between the
/// two standards it sits between. 8K is retired — everything ≥3840 is 4K.
static func resolutionClass(width: Int, height: Int) -> String {
    guard width > 0, height > 0 else { return "Unknown" }
    let long = max(width, height)
    if long >= 3840              { return "4K" }
    if abs(long - 2560) <= 2     { return "QHD" }
    if abs(long - 1920) <= 2     { return "1080p" }
    if long > 1920               { return "FHD" }
    if abs(long - 1280) <= 2     { return "720p" }
    if long > 1280               { return "HD" }
    return "SD"
}

/// Snap to nearest standard frame rate for filename generation.
/// Raw rate is preserved separately for display in identification rows.
static func fpsClass(_ fps: Float) -> Int {
    let targets = [30, 60, 120]
    return targets.min(by: { abs(Float($0) - fps) < abs(Float($1) - fps) })!
}

/// V = portrait (height > width), W = landscape (width >= height).
static func orientation(width: Int, height: Int) -> String {
    return height > width ? "V" : "W"
}
```

### 24.6 Boundary crossover tests

These tests verify every boundary transition point. They replace the old `testResolution_1080pIsNotFHD` and `testResolution_otherBuckets`.

```swift
func testResolutionBucketBoundaries() {
    // Fixed standards, with tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 3840, height: 2160), "4K")
    XCTAssertEqual(MediaClassification.resolutionClass(width: 7680, height: 4320), "4K")  // 8K folds into 4K
    XCTAssertEqual(MediaClassification.resolutionClass(width: 2560, height: 1440), "QHD")
    XCTAssertEqual(MediaClassification.resolutionClass(width: 2558, height: 1440), "QHD") // tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 2562, height: 1440), "QHD") // tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 1920, height: 1080), "1080p")
    XCTAssertEqual(MediaClassification.resolutionClass(width: 1918, height: 1080), "1080p") // tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 1922, height: 1080), "1080p") // tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 1280, height: 720), "720p")
    XCTAssertEqual(MediaClassification.resolutionClass(width: 1278, height: 720), "720p")   // tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 1282, height: 720), "720p")   // tolerance

    // FHD: between 1080p tolerance and QHD tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 1923, height: 1080), "FHD") // just outside 1080p tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 2557, height: 1440), "FHD") // just below QHD tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 2436, height: 1125), "FHD") // iPhone X screen recording

    // HD: between 720p tolerance and 1080p tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 1283, height: 720), "HD") // just outside 720p tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 1600, height: 900), "HD")
    XCTAssertEqual(MediaClassification.resolutionClass(width: 1917, height: 1080), "HD") // just below 1080p tolerance

    // SD: below 720p tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 1277, height: 720), "SD") // just below 720p tolerance
    XCTAssertEqual(MediaClassification.resolutionClass(width: 640, height: 480), "SD")
    XCTAssertEqual(MediaClassification.resolutionClass(width: 128, height: 224), "SD") // iMessage clip

    // Portrait: long edge is max(w, h)
    XCTAssertEqual(MediaClassification.resolutionClass(width: 1080, height: 1920), "1080p")
    XCTAssertEqual(MediaClassification.resolutionClass(width: 720, height: 1280), "720p")
    XCTAssertEqual(MediaClassification.resolutionClass(width: 2160, height: 3840), "4K")

    // Unknown / zero
    XCTAssertEqual(MediaClassification.resolutionClass(width: 0, height: 0), "Unknown")
}
```
